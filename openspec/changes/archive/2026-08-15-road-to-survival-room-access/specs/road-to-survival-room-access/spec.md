## Purpose

Lets a group of players start a private, account-free game session, share access to it with a code and password, and return to the same session later under their chosen username.

## ADDED Requirements

### Requirement: Room Creation
The system SHALL allow a user to create a new room by supplying only a username, with no account or prior registration required. On successful creation, the system SHALL automatically generate a unique room code and a unique room password for the room.

#### Scenario: Successful room creation
- **WHEN** a user submits a create-room request with a valid username
- **THEN** the system creates a new room, generates a unique room code and a unique room password, and returns both to the user along with the room code

#### Scenario: Username required to create a room
- **WHEN** a user submits a create-room request with an empty or missing username
- **THEN** the system rejects the request and creates no room

### Requirement: Creator Is Automatically Room Admin
The user who creates a room SHALL be designated as that room's admin at creation time, with no separate action required to acquire admin status.

#### Scenario: Creator flagged as admin
- **WHEN** a user creates a room
- **THEN** that user's player record in the room is marked as admin
- **AND** no other player in that room is marked as admin unless the admin's identity is later restored via rejoin

### Requirement: Room Code and Password Are System-Generated
Room codes and room passwords SHALL be generated by the system. Users SHALL NOT be able to choose or set a room's code or password.

#### Scenario: Client-supplied code or password ignored on creation
- **WHEN** a create-room request includes a proposed room code or room password
- **THEN** the system ignores the supplied values and generates its own unique room code and room password

### Requirement: Room Password Shown Once
The system SHALL return the room password to the creator at creation time and SHALL NOT expose the room password in plaintext through any other request afterward.

#### Scenario: Password included only in creation response
- **WHEN** a room is created
- **THEN** the create-room response includes the plaintext room password

#### Scenario: Password not retrievable later
- **WHEN** any user, including the admin, later requests information about an existing room
- **THEN** the response does not include the plaintext room password

### Requirement: Joining a Room
The system SHALL allow a user to join an existing room by supplying the room's code, the room's password, and a username that is not currently in use by another connected player in that room. On success, a new player record SHALL be created in that room for the username.

#### Scenario: Successful join with a new username
- **WHEN** a user submits a join request with a valid room code, the matching room password, and a username not already active in that room
- **THEN** the system admits the user to the room as a new, non-admin player

#### Scenario: Join with unknown room code
- **WHEN** a user submits a join request with a room code that does not match any room
- **THEN** the system rejects the request with a generic invalid-access error

#### Scenario: Join with incorrect password
- **WHEN** a user submits a join request with a valid room code but a room password that does not match that room's password
- **THEN** the system rejects the request with a generic invalid-access error that does not reveal whether the code or the password was wrong

### Requirement: Rejoining a Room
The system SHALL allow a user to resume a previously established identity in a room by supplying the room's code, the room's password, and the exact username of an existing player record in that room. On success, the system SHALL restore that player's previously persisted state, including admin status and last known game state.

#### Scenario: Successful rejoin restores prior state
- **WHEN** a user submits a join request with a valid room code, the matching room password, and a username matching an existing player record in that room
- **THEN** the system reconnects the user to that existing player record
- **AND** restores the player's previously persisted game state and admin status
- **AND** does not create a duplicate player record

#### Scenario: Rejoin works after the room's live process has stopped
- **WHEN** a user rejoins a room whose live game process had previously been stopped (e.g., due to inactivity or a server restart)
- **THEN** the system re-establishes a live process for that room, hydrated from persisted room and player data
- **AND** the rejoining player's state matches what was last persisted before the process stopped

### Requirement: Username Uniqueness Within a Room
Within a single room, no two simultaneously connected players SHALL share the same username. Usernames are scoped to a room and MAY be reused across different rooms.

#### Scenario: Duplicate active username rejected
- **WHEN** a user attempts to join or rejoin a room using a username that is already connected in that room from another active session
- **THEN** the system rejects the request without disconnecting the existing session

#### Scenario: Same username usable in a different room
- **WHEN** a username already in use in one room is used to create or join a different room
- **THEN** the system permits it, since username uniqueness is scoped per room

### Requirement: Persistent Room and Player State
The system SHALL durably persist each room's identity (room code, room password, admin designation) and each player's game state so that rejoining a room after its live process has stopped resumes the player's prior state rather than starting over.

#### Scenario: State survives a server restart
- **WHEN** the server process restarts after players have joined a room and moved within it
- **THEN** a subsequent successful rejoin by an existing player restores that player's game state as it was last persisted before the restart

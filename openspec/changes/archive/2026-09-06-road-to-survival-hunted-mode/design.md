## Context

See proposal.md - Why. Relevant current state:

- `server/src/rooms/schema/GameState.ts` defines the Colyseus-synced `GameState`: `PlayerState` (`sessionId`, `username`, `isAdmin`, `x`, `y`, `ready`) and `TimelineState` (`daysPerWeek`, `week`, `segment`, `phase`, `cards`).
- `server/src/rooms/GameRoom.ts` handles the `ready` message and `maybeAdvance`/`advanceSegment` (unanimous-ready or admin `override-segment` triggers advancement; `advanceSegment` also handles entering the `week-end` phase at the last segment and resets every connected player's `ready`), and the `vote-skill-check` message (writes to `SegmentCardOptionState.voters`, gated only on `timeline.phase === "active"`).
- Per `specs/road-to-survival-timeline-board`, advancement and admin actions are evaluated only against currently connected players (`[...this.state.players.values()]`), and reset readiness for the landed-on segment.
- Per the existing precedent on `daysPerWeek` (`GameRoom.ts` comment), ephemeral per-room-process state that isn't explicitly written to Postgres resets if the room's live process fully disposes and is later recreated (e.g. server restart). Card contents and votes are the exception, made durable via `RoomSegmentCard`/`RoomSegmentVote` (see the `road-to-survival-skill-check-cards` design).

## Goals / Non-Goals

**Goals:**
- Add a room-scoped `mode` (`normal` | `hunted`) the admin can toggle at any time, in either direction.
- Add a Hunted-Mode-only Forced March vote, majority-gated, where reaching a majority makes the timeline advance available for the admin to confirm rather than advancing it directly -- confirmation reuses the existing `advanceSegment` transition (including the week-end transition) so Hunted Mode doesn't fork timeline-advancement logic.
- Add a Lead-token count per player, admin-incrementable for all currently connected players, gated on a confirmed Forced March having just occurred.
- Gate `vote-skill-check` on holding at least one Lead token when the room is in Hunted Mode for a new vote or a change of option, but defer actually spending the token until the segment the vote was cast on is left -- via ready-up, a confirmed Forced March, or an admin's forward override.
- Let a player retract their own vote (in either mode) by casting a vote for the option they already have an active vote on, at no cost, without gating that on Lead-token count.
- Exclude the admin from casting a Forced March vote entirely, and from the majority calculation used to decide whether one is awaiting confirmation.
- Lock out Forced March voting entirely while any player holds an active skill-check vote on the current segment, and retroactively withdraw any in-progress Forced March (votes + awaiting-confirmation state) the moment a player casts or changes a skill-check vote in Hunted Mode.

**Non-Goals:**
- Persisting mode, vote, confirmation-availability, or Lead-token state across a full room-process recreation. Treated the same as `ready`/`daysPerWeek` today: it resets to `normal` / no votes / no tokens if the server restarts. A future change can extend the existing Prisma persistence if this proves disruptive in practice.
- Any narrative or mechanical consequence of being "hunted" beyond the voting/token rules described here (e.g. no roaming threat, no DM-facing danger meter). Purely a room-state + voting-permission feature.
- Configuring the Forced March majority threshold per room. Fixed at "more than half of currently connected players," matching the fixed (not room-configurable) nature of the existing unanimous ready-up threshold.
- A cap on how many Lead tokens a player may accumulate. The proposal specifies stacking with no stated limit, so none is enforced.

## Decisions

**Mode lives on `TimelineState`, not `GameState`, as `@type("string") mode: "normal" | "hunted" = "normal"`.** Every other piece of shared, admin-controllable room state that affects segment/voting behavior (`phase`, `daysPerWeek`) already lives on `TimelineState`; keeping `mode` there avoids introducing a second place to look for room-level game state.

**Forced March vote is a new per-player boolean, `skipVote`, on `PlayerState`, mirroring `ready`.** (Internal field/message names keep the existing "skip" terminology from before the client-facing rename to "Forced March" — only the UI copy changed, per the proposal.) Reusing the `ready` field itself was considered and rejected: ready-up and the Forced March vote are independent per the proposal (a player can be readied up and also vote for a Forced March), and conflating them would make one silently count as the other. A separate field keeps the two mechanics' state independent, matching how they're independent in behavior.

**Reaching a majority no longer advances the segment directly.** A new `TimelineState` flag, `skipConfirmationAvailable: boolean`, tracks whether a majority is currently met. `maybeSkip()` (invoked after a vote is cast and after a player disconnects, same call sites as before) recomputes this flag from scratch each time -- `players.filter(p => p.skipVote).length > players.length / 2` -- rather than latching it permanently once true, so a disconnect that drops the majority clears the flag again (per the proposal's "losing the majority before confirmation clears the awaiting state"). A new admin-only message, `confirm-skip`, is the only thing that calls `advanceSegment()` for this path: it's rejected unless `skipConfirmationAvailable` is true and the sender is the admin: on success it calls `advanceSegment()` (unchanged) and then sets `leadTokenAssignmentAvailable = true`.

**`skipConfirmationAvailable` is cleared inside `advanceSegment()`**, alongside the existing `leadTokenAssignmentAvailable` reset, so it never lingers once the segment it applied to has been left -- by confirmation, by ready-up, or by admin override. `confirm-skip` sets `leadTokenAssignmentAvailable = true` immediately after calling `advanceSegment()`, the same override-after-reset pattern already used for the old direct-advance path.

**Lead tokens are a per-player count, `leadTokens: number`, on `PlayerState`, not a boolean.** The proposal now specifies that tokens stack ("a player MAY hold more than one Lead token at a time"), so a boolean can no longer represent the state; `leadTokens` starts at `0` and is incremented/decremented by exactly one per assignment/vote, with no cap (see Non-Goals).

**`assign-lead-tokens` increments `leadTokens` by exactly one for every currently connected player**, unconditionally (adding to whatever count they already hold), then clears `leadTokenAssignmentAvailable`. A player who joins after assignment starts at their current count (0 if newly joined) until the next confirmed Forced March + admin assignment, consistent with "currently connected players" scoping used elsewhere.

**`vote-skill-check` first checks whether the incoming `optionIndex` matches the player's current vote on the card (found by scanning `cardState.options` for their username), and branches on that before anything else.** If it matches, this is a retraction: `deleteVote(cardId, roomPlayerId)` (new, see below) plus splicing the player's username out of that option's `voters` -- no Lead-token check, no other side effect. If it doesn't match (a new vote, or a change to a different option), the existing Lead-token gate applies when `timeline.mode === "hunted"` (`player.leadTokens <= 0` rejects, unchanged from before), followed by the existing `upsertVote` + voters-array move. **The decrement that used to happen here is removed entirely** -- consumption moves to `advanceSegment()` (below). In `normal` mode, casting/changing behavior is otherwise byte-for-byte unchanged from before this revision; retraction is new in both modes. Switching a room's mode to `normal` still resets every connected player's `leadTokens` to `0` (proposal's explicit choice), so tokens never silently carry over into a later Hunted-Mode session.

**`advanceSegment()` gains a step that consumes Lead tokens for the segment being left, run before `timeline.segment` is mutated.** A new private helper, `consumeLeadTokensForSegment(segment)`, looks up that segment's `cardState`, collects every username with an active vote across its four options, and -- only when `timeline.mode === "hunted"` -- decrements `leadTokens` by one (floored at zero) for each currently-connected player whose username is in that set. Because `advanceSegment()` is the single shared transition used by ready-up (`maybeAdvance`), `confirm-skip`, and the forward branch of `override-segment`, this one insertion point covers all three paths the proposal specifies as chargeable, with no per-path duplication. The backward branch of `override-segment` never calls `advanceSegment()`, so it's excluded automatically -- no extra guard needed.

  Iterating by username (not sessionId) means a player who voted and then disconnected before the segment resolves is *not* charged, since `this.state.players` (keyed by sessionId) no longer contains them at consumption time -- consistent with the pre-existing precedent that ephemeral per-player Hunted-Mode state (like `ready`) doesn't survive a disconnect/reconnect within the same live process either (see onJoin: only `x`/`y`/`isAdmin` are restored from Postgres, nothing Hunted-Mode-related).

**A new `deleteVote(cardId, roomPlayerId)` function in `db/segmentCards.ts`, alongside the existing `upsertVote`.** Implemented as `prisma.roomSegmentVote.deleteMany({ where: { cardId, roomPlayerId } })` rather than `.delete(...)` -- `deleteMany` is a no-op (not a throw) if the row is somehow already gone, which is simpler than wrapping a `.delete()` call in a not-found catch for a codepath that should always find exactly one row given the schema-state check that gates it.

**The client's per-option interactive/locked state can no longer be a single card-wide `votable` boolean.** Today (`MainScene.ts`'s `renderCard()`), one `votable` flag disables/enables all four rows uniformly. But now a player at 0 Lead tokens must still be able to click their *own* already-voted row to retract it, while the other three rows stay locked. `skillCheckCard.ts` gains a third pure helper, `canInteractWithOption(canPlaceVote: boolean, isOwnActiveVote: boolean): boolean => canPlaceVote || isOwnActiveVote`, and `renderCard()` computes `canPlaceVote = onCurrentActiveSegment && hasVotingRights(mode, leadTokens)` once, then calls `canInteractWithOption(canPlaceVote, i === currentVoteIndex)` per row (`currentVoteIndex` found the same way the server does: scanning the card's options for the local player's username). `onCurrentActiveSegment` still gates everything -- a player can't retract on a segment that isn't the room's actual current one, or outside the active phase, matching Voting Restricted to the Current Segment.

**`vote-skip` gains two more rejections, checked before recording the vote: the sender is the admin, or the room's actual current segment has an active skill-check vote (`timeline.currentSegmentHasActiveVote`, see below).** Both reuse the handler's existing early-return style (mode/phase checks already there).

**`maybeSkip()`'s majority calculation now filters to non-admin players for both the vote count and the total** -- `players.filter(p => !p.isAdmin)`, then `skipCount`/`length` computed against that filtered list instead of `this.state.players.values()` directly. Since `vote-skip` already rejects the admin, the admin's `skipVote` can never be `true` in practice, but filtering both sides keeps the calculation correct by construction rather than by the vote-skip guard alone.

**A new synced field, `TimelineState.currentSegmentHasActiveVote: boolean` (default `false`), tracks whether the room's actual current segment's card has at least one active skill-check vote.** A private `recomputeCurrentSegmentHasActiveVote()` helper sets it from `this.state.timeline.cards.get(String(this.state.timeline.segment))`, treating a missing card the same as no votes. It's called from every site that changes either which segment is current, or what votes exist on the current segment's card: both branches of `vote-skill-check` (cast/change, and retraction), the end of `advanceSegment()`, the backward branch of `override-segment`, the week-rollover branch of `resolve-week-end`, and once after the initial `ensureWeekCards` load in `onCreate` (covering a room recreated from a segment that already has persisted votes). Keeping it as an explicit synced flag (rather than having the client re-derive it from the replicated `cards` map) matches the existing pattern for other derived room-level gates (`skipConfirmationAvailable`, `leadTokenAssignmentAvailable`), and avoids the client having to reactively track nested `ArraySchema` mutations inside a `MapSchema` just to render one button's disabled state.

**The cast/change branch of `vote-skill-check` also calls a new `clearForcedMarchVotes()` helper, when `timeline.mode === "hunted"`, immediately after recording the vote.** It resets every connected player's `skipVote` to `false` and `timeline.skipConfirmationAvailable` to `false` -- unconditionally on every cast/change (not gated on "was this the segment's first active vote"), which is simplest to reason about and idempotent when there was nothing to clear. The retraction branch never calls it: per the proposal, only casting or changing a vote withdraws an in-progress Forced March, not retracting one.

**Client: the Forced March button's `disabled` boolean becomes a small reason-string helper in `gameHud.tsx`.** Something like `forcedMarchDisabledReason(me, timeline): string | null`, checked in order: the local player is the admin ("The admin doesn't vote on the Forced March."), then `timeline.currentSegmentHasActiveVote` ("Someone has already voted to roll a check this segment."), then the player's own `skipVote` already being `true` (existing "Marching!" case, no extra explanation needed beyond the label). `disabled = reason !== null`; the reason (when non-null and not just the player's own already-cast vote) renders as a short hint under the button, the same spot a validation/status message would go. The majority progress readout (`count/total`) is also updated to filter out the admin from both, mirroring the server's `maybeSkip()` change, so the displayed fraction matches what the server is actually evaluating.

**No new Prisma models or migration.** `deleteVote` uses the existing `RoomSegmentVote` table and its existing `(cardId, roomPlayerId)` unique index -- no schema change. All new room-state fields remain Colyseus-only (see Non-Goals), so there's nothing further to persist.

## Risks / Trade-offs

- [Mode/vote/confirmation/Lead-token state resets on a full room-process recreation (server restart mid-Hunted-Mode-session)] → Accepted, consistent with the existing `daysPerWeek`/`ready` precedent; not a regression relative to today's behavior for other ephemeral room state.
- [A player who disconnects and reconnects mid-vote loses their own recorded Forced March vote, same as `ready` does today] → Accepted as existing, intentional behavior for readiness-style voting; not a new inconsistency introduced by this change.
- [A majority is reached and then lost before the admin gets to confirm (e.g. a fast disconnect), silently withdrawing the confirm affordance mid-decision] → Accepted per the proposal's explicit requirement; the admin's next confirm attempt is simply rejected, and a new majority re-enables it.
- [Two independent boolean flags per player (`ready`, `skipVote`) plus a `leadTokens` count slightly grows `PlayerState`, and a client that doesn't yet know about Hunted Mode would simply not render the new fields] → Acceptable; Colyseus schema additions are additive and don't break existing fields.
- [Stepping a segment backward via admin override and then forward again re-triggers `consumeLeadTokensForSegment` for whatever votes are still recorded on that segment's card, double-charging any player who never changed their vote in between] → Accepted; there's no per-card "already resolved" bookkeeping, and this only happens via the admin-only backward-override tool, which is already documented (in the original Admin Override design) as a rare correct-a-mistake action, not a normal-play path.
- [A vote cast while the room was in "normal" mode (no token cost at cast time) can still be charged a token if the admin switches to "hunted" mode before that segment advances, since consumption keys off the room's mode *at advance time*, not at the time the vote was cast] → Accepted as a narrow, low-frequency edge case; tracking per-vote "which mode was I cast under" would add real state for a scenario the proposal doesn't call out, and the ordinary flow (mode set once, before play in that mode begins) never hits it.
- [The admin sees the Forced March button at all times in Hunted Mode, permanently disabled, rather than it being hidden] → Accepted, matches the proposal's explicit "disabled with a message" requirement; keeps the admin able to see the live vote tally even though they can't contribute to it.
- [A single player casting a skill-check vote can silently discard a majority the rest of the party just spent effort reaching, with no confirmation step of its own] → Accepted per the proposal's explicit "retroactively clears" requirement; modeled as an intentional in-fiction trade-off (committing to a roll means abandoning the march), not an accidental side effect to guard against.
- [The Forced March lockout, combined with the retroactive clear, makes it provably impossible to ever reach a confirmed Forced March while any player holds an active skill-check vote -- so the earlier "a confirmed Forced March consumes tokens for active voters" scenario (see Lead Token Consumed When a Segment Advances) can now only ever find zero active votes in practice] → Accepted; `consumeLeadTokensForSegment` stays wired into `advanceSegment()` unconditionally (harmless no-op for this path), and only ready-up and the admin's forward override remain the paths that actually consume a token while votes are active.

## Migration Plan

- Purely additive schema/state changes (`TimelineState.mode`, `TimelineState.skipConfirmationAvailable`, `TimelineState.leadTokenAssignmentAvailable`, `TimelineState.currentSegmentHasActiveVote`, `PlayerState.skipVote`, `PlayerState.leadTokens`) plus new message handlers (`set-mode`, `vote-skip`, `confirm-skip`, `assign-lead-tokens`), plus behavior-only changes to the existing `vote-skill-check` handler, `maybeSkip()`, and `advanceSegment()`, plus a new `deleteVote` function in `db/segmentCards.ts` against the existing `RoomSegmentVote` table. No database migration. No rollback concerns beyond reverting the code change — no persisted data shape changes.

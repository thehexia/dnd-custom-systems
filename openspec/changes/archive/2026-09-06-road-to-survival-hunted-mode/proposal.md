## Why

Right now every room runs the same way: any connected player can vote on a segment's skill-check card, and the timeline only moves forward when everyone readies up. There's no way for the admin to raise the tension by restricting who gets a say, or to let the party trade a faster pace for that restriction. Hunted Mode adds an admin-toggled room state where advancing quickly costs something: skipping a segment requires a party vote, and only players holding a "Lead" token — handed out by the admin after a successful skip vote — can vote on skill-check rolls.

## What Changes

- Add a per-room mode toggle, `normal` / `hunted`, that only the admin can switch, at any time, in either direction. Switching to `normal` clears every player's held Lead tokens.
- In Hunted Mode, add a segment-skip vote, presented to players as "Forced March": any connected **non-admin** player can cast a vote for it — the admin never votes for it, only confirms it (see below). When a simple majority of currently connected non-admin players have voted, the room enters an awaiting-confirmation state rather than advancing automatically. Only the admin can confirm it; confirming is what actually advances the timeline (the same transition as full ready-up, including entering the week-end decision state if the last segment of the week is skipped) and clears every player's vote. If the majority is lost before the admin confirms (e.g. a voter disconnects), the awaiting-confirmation state clears and the admin can no longer confirm until a new majority is reached.
- Forced March voting locks out entirely while any player has an active skill-check vote on the current segment: the instant one connected player has voted to roll a check on that segment's card, no player (including the admin, already excluded above) may cast a new Forced March vote, until every active vote on that segment is retracted. Casting a new skill-check vote, or changing to a different option (not retracting), while the room is in Hunted Mode also retroactively withdraws any in-progress Forced March — every player's Forced March vote is cleared, and an already-reached majority awaiting the admin's confirmation is revoked too. The client's Forced March button reflects both lockouts by rendering disabled with an explanation, rather than silently rejecting the click.
- A confirmed Forced March unlocks a one-time admin action to assign a Lead token to every currently connected player. The admin may use it or let it lapse; it is not automatic.
- **BREAKING** (Hunted Mode only): while a room is in Hunted Mode, a player without at least one Lead token cannot cast a new skill-check vote or change to a different option. A player MAY hold more than one Lead token at a time: each admin assignment grants one additional token to every currently connected player, stacking on top of any they already hold, rather than replacing what they hold. This does not change voting in Normal Mode.
- A Lead token is NOT spent the moment a player votes. It's only actually consumed when the segment the vote was cast on is left — via ready-up, a confirmed Forced March, or an admin's forward override — at which point every currently connected player who still has an active vote recorded on that segment's card loses exactly one Lead token. An admin stepping the timeline backward never consumes a token. This means a player can freely change their mind about a vote for as long as the segment remains current, without losing anything.
- Any player, in either mode, MAY retract their own vote by casting a vote for the option they already have an active vote on — this removes the vote instead of re-recording it, leaves them with no active vote on that card, and never requires or consumes a Lead token (see the `road-to-survival-skill-check-cards` capability).
- The Forced March vote is independent of the existing ready-up mechanic; both remain available at the same time in Hunted Mode. The vote is only accepted while the timeline phase is "active", evaluated only against currently connected players (consistent with existing readiness handling), and the confirm and assignment actions are rejected for a non-admin, or outside Hunted Mode.

## Capabilities

### New Capabilities
- `road-to-survival-hunted-mode`: admin-controlled Normal/Hunted mode toggle for a room, the Hunted-Mode Forced March vote (non-admin players only, majority evaluated over non-admin players, locked out while any skill-check vote is active on the current segment, and retroactively cleared by a new/changed skill-check vote) and its majority-then-admin-confirmation flow, admin assignment of stackable Lead tokens to connected players following a confirmed Forced March, and Lead-token consumption deferred until the segment a vote was cast on actually advances.

### Modified Capabilities
- `road-to-survival-skill-check-cards`: casting a new skill-check vote or changing to a different option while the room is in Hunted Mode requires the voting player to hold at least one Lead token (consumption itself now lives in the `road-to-survival-hunted-mode` capability, tied to segment advancement); a player may retract their own vote, in either mode, by re-selecting the option they already voted for, at no cost.

## Impact

- Server: `games/road-to-survival/server/src/rooms/GameRoom.ts` gains message handlers for `set-mode` (admin-only), `vote-skip`, `confirm-skip` (admin-only, gated on a reached majority), and `assign-lead-tokens` (admin-only, gated on a confirmed Forced March); the existing `vote-skill-check` handler gains a Lead-token eligibility check gated on the room's mode, plus retraction handling (removing a vote instead of moving it, when the player re-selects their current option); and `advanceSegment()` gains a step that consumes Lead tokens for the segment being left, in Hunted Mode. `vote-skip` additionally rejects the room's admin and rejects while the current segment has an active skill-check vote; `maybeSkip()`'s majority calculation excludes the admin from both the vote count and the total; the cast/change branch of `vote-skill-check` clears any in-progress Forced March vote (every player's `skipVote`, plus `skipConfirmationAvailable`) when the room is in Hunted Mode; and every site that changes what `timeline.segment` points to, or what votes exist on it, recomputes a new `currentSegmentHasActiveVote` flag.
- Server persistence: `games/road-to-survival/server/src/db/segmentCards.ts` gains a `deleteVote` function so a retraction removes the corresponding `RoomSegmentVote` row, alongside the existing `upsertVote`.
- Server schema: `games/road-to-survival/server/src/rooms/schema/GameState.ts` gains a mode field (likely on `TimelineState` or `GameState`), a per-player `leadTokens` count on `PlayerState`, a per-player skip-vote flag mirroring `ready`, a flag marking whether a majority Forced March vote is awaiting admin confirmation, a flag marking whether a Lead-token assignment is currently available to the admin, and a `currentSegmentHasActiveVote: boolean` flag tracking whether the room's actual current segment's card has any active skill-check vote.
- Client: `games/road-to-survival/client/src/ui/gameHud.tsx` (or equivalent) gains an admin-only mode toggle control, a "Forced March" vote control visible to all players in Hunted Mode (disabled with an explanatory message for the admin, or while a skill-check vote is active on the current segment), an admin-only "Confirm Forced March" control that appears once a majority is reached, an admin-only "assign Lead tokens" control that appears after a confirmed Forced March, and a per-player Lead-token count indicator; the skill-check card UI (`client/src/scenes/MainScene.ts`) gains a Hunted-Mode-aware disabled/locked state for players holding no Lead tokens, and must keep a player's own already-voted option clickable (to retract) even when they hold zero tokens.
